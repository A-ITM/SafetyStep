# 세이프티스탭 1.2 피드백 검토와 1.3 반영

검토일: 2026-11-17 · 대상: 실행 계획 1.2, 기존 기획서, 현재 0.5 코드/SDK 기록

**무응답 후보 경로에서 위험 공유가 막힐 수 있다는 지적은 맞다.** 1.2의 ‘후보만으로 확정 제보 없음’이 사고 확정과 정차 관측 공유를 함께 막았다. [실행 계획 1.3](safetystep-execution-plan.md)은 두 조건을 분리한다. 다만 저속 수신의 모든 경고 억제, 역지오코딩으로 도로 방향 확정, 필드 존재만으로 공공 사건 종료 판정은 채택하지 않는다.

이번 작업은 계획·근거 검토다. 앱 구현, API 키 신청, 외부 문의, 실기동 시험, 기획서 원본 수정은 수행하지 않았다.

## 2. 그대로 채택하면 생기는 문제와 보완

### 2.1 공유 조건을 바꿔도 자동 기동의 미지원이 해결되지는 않음

사전 동의, 신선한 차량·위치 관측, 허용된 앱 실행 상태, 통신 경로가 필요하다. 이 조건이 있어야 응답 없이 전파할 수 있다. 앱이 실행되지 않고 신호도 수신하지 못하는 환경까지 무응답 전파를 보장하지 않는다. W00 지원표와 W02/W07 생명주기 시험은 계속 필수다.

정차 시간·도로/시설 구분·신선도·위치 정확도는 W01에서 정한다. 비상등을 필수 ON으로 두면 켤 수 없는 탑승자가 다시 누락되므로 보조 관측으로 둔다. 본선/갓길 위치를 구분할 수 없는 SDK가 차로를 판별한 것처럼 표시해서도 안 된다. 정체 속 정차 공유의 과잉 알림과 데이터 비용도 시험 결과에 남긴다.

정차 관측을 추가하면 해제 정책도 필요하다. 서버가 검증한 재출발 관측으로 자신의 STOPPED_VEHICLE만 철회하는 경로를 계약에 넣는다. 그것을 사고 해소나 도로 안전 판정으로 쓰지 않고, 다른 사고/공공 사건은 유지한다. TTL·통신 단절·구간 이탈만으로 해소 처리하지 않는다.

### 2.2 ‘저속이므로 위험 없음’은 성립하지 않음

저속 보류는 정차 관측의 첫 음성에 제한한다. 관련 위험 카드는 남기고, 속도가 오르거나 거리가 좁혀지면 미발화 첫 경고를 다시 판단한다. 속도 불명·근접 위험·확인 사고까지 일괄 억제하지 않는다. 구체 속도·지속시간·근접 기준과 재평가 fixture를 W01에서 고정한다. 억제된 알림을 전달 성공으로 집계하지 않는다.

이 재평가는 ‘첫 경고를 아직 하지 않은 경우’다. 이미 경고한 사건을 감속 여부로 다시 말하는 기능과 구분한다.

### 2.3 재경고보다 먼저 검증할 차별화 가설

작은 재경고 함수에도 감속 기준, 이미 감속 중인 차량, 오디오 경합, 센서 불명, 사고 지점 통과, 과잉 안내 검수가 붙는다. 범위 축소를 유지하면서 **자체 관측의 선행 시간 측정**을 먼저 넣는다. 서버 구조나 payload를 재경고용으로 늘리지 않는다.

Δ는 같은 사건이라고 대조한 자체 정보와 공공 정보의 최초 수신 시각 차이다. 두 소스가 늦거나 순서가 바뀌는 결과도 그대로 보고한다. 공공 정보가 관찰 기간 안에 없으면 미관측으로 기록한다. 같은 사건인지 불확실한 자료를 임의로 짝짓거나, 모의 공공 지연을 만들어 우위를 입증했다고 하지 않는다. 다른 내비 제품을 직접 비교하지 않았으므로 ‘내비보다 빠르다’는 결론도 내리지 않는다.

## 3. 공식 자료·설치 SDK 확인

### 3.1 UTIC와 Supabase: 직접 연결 제약 확인

UTIC 공식 돌발정보 레퍼런스는 키 값과 IP 인증을 명시한다. Supabase 공식 문서는 Edge Functions가 고정되거나 안정적인 송신 IP를 제공하지 않는다고 설명한다. 따라서 기본 Edge Function에서 UTIC에 직접 요청하는 구조는 IP 등록 조건과 맞지 않을 수 있다. 리전 고정만으로 고정 송신 IP가 생긴다고 가정하지 않는다. [UTIC 공식 레퍼런스](https://www.utic.go.kr/guide/utisRefIncident.do), [Supabase 공식 설명](https://supabase.com/kb/troubleshooting/why-supabase-edge-functions-cannot-provide-static-egress-ips-for-whitelisting-3d78b0)

선정 순서는 서버 실행 환경에 맞는 원천 검토 → 실제 인증/응답 확인이다. UTIC가 꼭 필요할 때만 고정 송신 IP 수집기의 비용·운영·호출 제한을 별도 검토한다. 이번 계획에 새 수집 서버를 자동으로 추가하지 않는다.

### 3.2 ITS: 유력 후보이나 현재 API 연결 검증은 남음

국토교통부의 2023년 기본교통정보 교환 기술기준 문서에는 공개키·좌표 범위 요청과 linkId·roadDrcType·endDate 등의 돌발정보 항목이 있다. 도로 방향과 링크는 불명일 수 있다. 이번 조회에서 ITS 서비스 상세 페이지가 타임아웃되어 **현행 API의 인증·할당량·실제 응답·종료 의미까지 확인하지는 못했다.** 기술기준의 필드 목록을 현재 서비스 접속 성공으로 바꾸지 않는다. [국토교통부 기술기준 원문](https://www.codil.or.kr/filebank/moct2014/202301/MOCT2998_0.PDF?nserialno=2998), [국가교통정보센터 확인 대상](https://www.its.go.kr/opendata/opendataList?service=event)

W00은 실제 문서/키로 인증 요건, 방향 값의 의미, 갱신 시각, 종료일이 예정인지 확정인지, 목록에서 사라지는 의미를 확인한다. `endDate`라는 이름이나 시각 경과만으로 RESOLVED를 만들지 않는다.

### 3.3 NaviHelper: API와 데이터 필드 확인, 에뮬레이터 응답은 미시험

공식 샘플에 `getCurrentLocationInfo()`와 `onCurrentLocationInfo()`가 있다. 현재 저장소의 NaviHelper 3.0.5 의존성과 호스트 캐시의 navi-data 3.0.4를 읽기 전용으로 확인했다. `CurrentLocationInfo`의 public accessor는 latitude, longitude, heading, address, routeId, currentRouteIndex다. 자료형 존재는 실제 값 제공이나 위치 정확도의 보장이 아니다. [공식 NaviHelper 샘플](https://github.com/Pleos-Playground/pleos-sample-navi-app), [API 호출·콜백 구현](https://github.com/Pleos-Playground/pleos-sample-navi-app/blob/main/app/src/main/java/ai/pleos/playground/navidevapp/screen/vm/NaviHelperViewModel.kt)

W00에서 경로 안내 유무·에뮬레이터 위치 변경·주소 누락·현재성 확인을 수행하고 W04에서 신고용 표시를 연결한다. heading만으로 ‘부산 방향’, ‘상행’처럼 도로 방향을 확정하지 않는다. 유효한 주소/좌표가 먼저이며 미확인 항목은 분리한다.

Android Geocoder는 네트워크를 사용할 수 있고 결과의 가용성·정확도를 보장하지 않는다. 공식 API는 안전 관련 판단에 쓰지 말라고 명시한다. 따라서 ‘기기 내 역지오코딩이면 오프라인 신고 위치·도로 방향이 해결된다’는 전제는 제외했다. [Android Geocoder API](https://developer.android.com/reference/android/location/Geocoder)

### 3.4 비트박스와 앱용 첫 문장은 구분

정부 정책브리핑에 수록된 한국도로공사 캠페인은 비상등·트렁크·차 밖 대피·스마트폰 신고를 설명한다. 1.3의 첫 핵심 음성은 트렁크 조작을 대피 전 필수 과제로 추가하지 않는 앱 설계안이다. 도로공사가 이 축약 문장을 승인했다고 표현하지 않는다. W01이 공식 근거, 적용 조건, 원문과의 차이를 기록하고 W10에서 검토한다. [도로공사 캠페인 자료를 수록한 정부 안내](https://www.korea.kr/news/policyNewsView.do?newsId=148931463)

## 5. 서비스 기획서 교체 문안

아래는 기존 기능/시나리오/개발 방법을 1.3 범위에 맞춘 **교체안**이다. 실측하지 않은 기능은 설계·개발 예정 표현을 유지했다. 실제 DOCX에는 아직 적용하지 않았다.

### 기능 ② — 행동을 먼저 안내하고 도움 요청을 듣는 대응

사고·고장 대응이 필요한 근거와 정차가 확인되면 짧은 행동 안내를 먼저 제공하고, 이동이 어렵거나 도움이 필요한 탑승자의 응답을 듣습니다. 역할 확인이나 여러 질문의 응답을 대피 안내의 선행 조건으로 두지 않습니다. 무응답·인식 실패·오디오 중단을 구분하고, 무응답만으로 의식불명을 판정하지 않습니다. 단순 정차 후보는 사고로 단정하지 않고 제한적으로 상황을 확인합니다.

### 기능 ③ — 비상등 확인·잔류 알림·신고 정보

비상등의 실제 상태를 확인하고 필요한 짧은 안내를 제공합니다. 좌석 관측으로 차 안에 남아 있을 가능성을 알리며, 좌석이 비었다는 이유만으로 안전지대 도착을 확정하지 않습니다. 확인 가능한 현재 위치와 연락 정보를 제공하고 완료 조작을 위해 차량으로 돌아오도록 요구하지 않습니다. 첫 구현의 필수 흐름에서 트렁크 제어와 개방 대기를 제외합니다. 행동 문구는 도로공사 안내를 근거로 적용 조건과 앱용 축약 내용을 구분해 검토합니다.

### 기능 ④ 및 시나리오 3) — 응답과 독립적인 정차 관측 공유

공공 돌발정보 1종을 기본 경고원으로 활용하고 앱 차량의 정차 관측으로 보완합니다. 사전 공유 동의와 도로·위치·정차 지속 등 관측 조건을 충족하면 탑승자 응답을 기다리지 않고 ‘정차 차량’으로 전달합니다. 사고 확정과 정차 관측을 구분하며 무응답·인식 실패를 공유 중단 조건으로 두지 않습니다. 다만 실행·위치·통신 조건이 충족되지 않으면 미전송 또는 상태 미확인으로 표시합니다. 구조 접수나 도로 안전이 확인된 것처럼 안내하지 않습니다.

### 개발 방법 5-2) — 시작 조건과 공유 조건

지원 사고 신호와 플랫폼 자동 기동 가능 범위를 검증하고, 미지원 환경에서는 명시적 시작 및 제한된 보조 후보 경로를 제공합니다. 정체·휴게소·요금소·졸음쉼터 정차를 사고 대응으로 오인하지 않는지 시험합니다. 대피 안내 시작과 정차 관측 공유는 별도 규칙으로 처리하며 무응답 상태에서도 공유 조건을 충족하면 전달합니다. 단순 후보만으로 사고를 확정하거나 차량 제어를 실행하지 않습니다.

### 개발 방법 5-4) — 공공 원천·Supabase HTTP 전파

서버 실행 환경의 인증·송신 IP·호출량 조건과 맞는 공공 돌발정보 1종을 선정합니다. ITS를 우선 검토하고 UTIC는 IP 인증 제약을 확인한 뒤 판단합니다. 자체 사건은 Supabase 인증·데이터베이스에 저장하며 앱의 현재 위치·방향에 맞춰 서버가 필터한 HTTP 목록으로 전달합니다. Realtime과 전국 도로 확장은 첫 구현에서 제외합니다. 원음·생체·좌석·도움 상태는 공유 payload에 넣지 않습니다. 출처·관측 시각·갱신 상태와 사건별 종료를 구분하고, 주행 UX 제한 아래 화면·음성 전달을 검증합니다.

### 이용·효과 검증 보완

사용자는 정차 중 수신 기능을 설정하고 다음 주행에는 이전 설정을 복원합니다. 실제 수신 가능 상태와 설정을 구분하며, 활성 수신 상태로 주행한 차량을 이용 지표에 반영합니다. 지원 입력 이후의 안내 지연뿐 아니라 최초 관측부터 안내까지의 전체 시간을 측정합니다. 같은 사건의 자체 관측·공공 정보 수신 시각을 비교하고, 미경고·늦은 경고·공공 미관측도 결과에 포함합니다. 약 20명 비교와 장기 유지율은 실제 관측을 마친 뒤 결과로 제시합니다.

## 6. 검토 범위와 결과

- 기획서의 기능 ②~④·무응답 시나리오·개발 5-2/5-4를 기존 추출 내용과 대조했다.
- 1.3의 I01/I03, 사건 유형·철회 권한, 평상시 수신, 신고 위치 담당, N_total/H/Δ, W 카드와 G 조건을 함께 갱신했다.
- 공유 조건을 만족한 무응답·비상등 OFF, 정체 저속 억제 후 재가속, 위치/동의 부족, 정차 관측 철회, 공공 미관측 시험을 추가했다.
- 설치된 SDK의 자료형은 읽었지만 에뮬레이터·마이크·실제 공공 API 호출은 하지 않았다. 원래 앱/서버 코드는 변경하지 않았다.
- 별도 모델의 구현 검증이나 실도로 효과 입증을 수행한 것으로 보고하지 않는다. 다음 단계는 W00/W01의 실제 지원 확인과 수치·계약 확정이다.
