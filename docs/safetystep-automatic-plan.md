# 세이프티스탭 자동 대응 프로토타입 계획

2026-11-15 · 0.5 · 이전 화면 중심 구현 계획을 대체한다.

## Phase 1. 기존 내용 검토 — 완료

기획서의 문제는 사고 직후 당황하거나 다친 사람이 안내를 찾아 읽고 화면을 조작하기 어렵다는 것이다. 응답해야만 지원을 시작하거나 비트박스 항목을 사용자가 직접 완료 처리하는 흐름은 문제 정의에 맞지 않는다.

근거: 서비스 기획서 개정본, `ui-state-and-theme-spec.md`, `safetystep-demo-audit.md`, FigJam v0.5 [45:614](https://www.figma.com/board/l8dy5wsdyoMRrpzldea2We?node-id=45-614), Figma [S4 1:812](https://www.figma.com/design/QuiuuWbKFqSNjSHQmOKIOX?node-id=1-812), 현재 코드와 에뮬레이터 기록. 비트박스는 [정부 안내](https://www.korea.kr/news/policyNewsView.do?newsId=148931463)를 참고하되 후방 충돌의 트렁크를 무조건 개방하지 않는다.

확인한 차이:
- 화면 단계와 버튼이 서비스 진행을 막았다. 자동 갱신할 사실과 사람에게 물을 판단을 분리해야 한다.
- 비상등 조회는 검증됐지만 앱의 자동 켜기 명령은 아직 없다. 콘솔 조작을 자동 실행의 증거로 삼을 수 없다.
- 실제 좌석 조회·음성 SDK·사건 전달은 재사용한다. 빈 좌석이 안전한 장소 도착을 증명하지는 않는다.
- 외부 콘솔은 재현 조건·관측 사실을 설명하고 앱만 운전자에게 말한다.
- 앞선 영상은 최종본에서 제외한다. 이번 검수가 끝난 뒤 촬영한다.

## Phase 2. 구현 계획 — 확정

### 고정된 사고 대응 화면

기본 Pleos 차량 화면과 내비게이션을 유지하고 우측 앱 패널에 다음을 고정한다.
1. 지금 필요한 짧은 안내와 음성 상태.
2. 좌석별 착좌 상태: 남은 탑승자, 이번 사건에서 비워진 좌석, 처음부터 빈 좌석, 확인 불가.
3. 비트박스 현황: 비상등 실제 켜짐 / 트렁크 조건 보류 또는 실제 열림 / 차 안의 탑승 상태 / 안전한 곳에서 스마트폰 신고.

응답·이동 가능·차량 제어·착좌·도로 사건은 별도 상태다. 다음/완료 버튼으로 넘기지 않는다. 도움 요청과 음성 실패 시의 큰 보조 입력만 남긴다. 차 안이 비면 IVI 조작이나 차량 복귀를 요구하지 않는다.

### 실행 계약

| 입력 | 앱 동작 | 완료 근거 |
| --- | --- | --- |
| 지원 대상 사건 접수 | 비상등 ON, 음성 질문, 도로 사건 등록을 독립 시작 | 각 동작의 실제 결과 |
| 비상등 이미 켜짐 | 중복 제어 없이 상태 표시 | 신선한 HAZARD_LIGHTS_STATE |
| 비상등 꺼짐/불명 | 지원·권한 확인 후 사건별 ON 1회, 실제 상태 재조회 | 명령 접수가 아닌 ON readback |
| 질문 재생 완료 | 실제 SDK 음성 인식, 응답과 이동 가능 확인 | 인식 문장·분류 결과 |
| 이동 가능 + P·속도 0 | 주변을 살피고 안전한 쪽으로 이동하도록 음성 안내 | 사용자 보고 + 실제 정차 |
| 후방 충돌 또는 방향 불명 | 트렁크 보류, 다른 지원 계속 | 충돌 맥락; 후방 공간 추정 금지 |
| 운전석만 비워짐 | 동승자 잔류 표시 | 전체 지원 좌석의 신선한 관측 |
| 관측한 탑승자 모두 좌석을 비움 | 떨어져 머물며 스마트폰으로 신고할 안내, 버튼 제거 | 모든 지원 좌석의 지속적인 빈 상태; 안전지대 도착으로 표현하지 않음 |

비상등 명령은 사건별 시도 기록을 저장하고 재구성·테마 변경·Activity 재생성 시 반복하지 않는다. 실패/시간 초과를 성공 처리하거나 자동 재시도하지 않는다. 이후 실제 켜짐을 관측하면 표시만 갱신한다. 모든 차량 접근은 VehicleGateway를 통하며 차량 제어는 디버그 에뮬레이터에서만 실행한다.

### 예외와 검증 경계

- 정상 청취 후 무응답: 재질문 한 번, 이후 응답 미확인. 의식 없음으로 판정하지 않는다.
- 재생/인식 오류: 음성 오류로 분리하고 보조 입력을 제공한다. 비상등·전파는 계속한다.
- 도움 요청/이동 곤란: 일반 질문 중단. 무리한 이동을 유도하지 않고 연락 수단 표시. 실제 전화 시험 없음.
- 이동 중/정차 불명: 하차·트렁크 보류. P만으로 정차 판정하지 않는다.
- 착좌 누락·오래된 값·오류: 빈 좌석으로 바꾸지 않는다. 운전석 하차만으로 전원 하차 처리하지 않는다.
- 통신 단절: 로컬 지원 유지, 전파 상태 별도 표시. 하차·단절·만료로 도로 사건을 종료하지 않는다.
- 실제 Pleos Vehicle Service·TTS/STT SDK·로컬 사건 전달을 사용한다. 재현 가능한 음성 시험은 합성 음성을 실제 STT에 입력한다. 노트북 마이크 권한은 변경하지 않는다.
- 외부 사고 이벤트는 검증용 입력이다. 에어백 기반 콜드 스타트와 Gleo 자체 선제 호출을 구현 완료로 주장하지 않는다. 별도 차량의 동일 사건 수신은 영상 외 검사로 충분하다.

## Phase 3. 계획 검수 — 통과

| 질문 | 결정 |
| --- | --- |
| 앱을 눌러야 시작하는가? | 외부 사고 입력 후 정상 흐름 앱 터치 0회. 자동 비상등·음성·착좌를 각각 입증 |
| 단계를 넘기는 체크리스트인가? | 고정 현황판. 관측 근거가 있을 때만 체크 |
| 명령 접수만으로 성공하는가? | 금지. 실제 켜짐 조회 필요 |
| 후방 충돌에서 트렁크가 열리는가? | 금지. 보류 및 명령 0회 검사 |
| 음성 실패가 전체 지원을 막는가? | 금지. 차량 제어·전파 독립 실행 |
| 센서가 안전한 대피/의식을 증명하는가? | 금지. 착좌·응답의 확인 범위만 표시 |
| 대피 후 전화 버튼이 남는가? | 모두 좌석을 비운 뒤 버튼 제거, 스마트폰 안내 유지 |
| 영상이 연동 범위를 과장하는가? | 사고 입력·음성 시험 방식은 콘솔과 검수 문서에 기록. 앱에 긴 기술 설명은 넣지 않음 |

남은 기술 위험은 비상등 쓰기 지원이다. 설치 SDK의 타입·권한·capability와 실제 ON readback을 확인한다. 지원이 없으면 그 사실을 기록하며 콘솔 켜기를 앱 성공처럼 사용하지 않는다.

## Phase 4. 구현 — 완료

비상등 자동 제어·중복 방지 → 고정 현황판·예외 안내 정리 → 시나리오의 비상등 켜기와 앱 버튼 입력 제거 → 검수 도구 갱신.

## Phase 5. 검수 — 통과

- 필수 `./scripts/check-android.sh`: 두 flavor 빌드·lint·단위 테스트.
- 실제 에뮬레이터: 정상 음성, 무응답, 인식 오류, 도움 요청, 운전석 하차/동승자 잔류, 전원 좌석 비움, 테마 전환.
- 비상등 OFF→사고→앱 요청→실제 ON, 이미 ON, 실패/미확인, 동일 사건 중복 실행 방지.
- 전원 좌석 비움 후에도 도로 사건 ACTIVE, 후방 충돌 트렁크 명령 0회, 같은 사건 수신.
- 라이트/다크·우측 패널에서 좌석·비트박스·보조 버튼의 잘림/정렬을 캡처로 확인.

## Phase 6. 영상 — 완료

사고 전 주행 → 후방 충돌 → 자동 비상등·음성 확인 → 이동 안내 → 운전석 하차·동승자 잔류 → 전원 좌석을 비운 후 지원 유지. 외부 상황/기존 Pleos 콘솔과 실제 차량 화면을 함께 촬영한다. 앱 터치 0회. 프레임·길이·화면을 확인한 영상, 검수 기록, APK를 로컬로 제공한다.


### Phase 3 재검수: 비상등 연동 경계 변경

실행 결과 `CONTROL_CAR_LIGHTS` 부여와 쓰기 capability(access=3, ON=1)에도 Vehicle Service가 `800001 ERROR_SECURITY_PERMISSION`으로 거절했다. 비상등 제어는 공개 Light API에 직접 노출되어 있지 않다. 기본 VEHICLE_SERVICE 모드는 이 실패를 그대로 보고하고 자동 재시도하지 않는다.

영상/동작 검수는 파일로 명시 선택한 `EMULATOR_CONSOLE` 어댑터를 사용한다. 앱 → 에뮬레이터 내부 기존 Virtual Console의 비상등 ON → Vehicle Service 실제 readback이다. 사용자 버튼이나 영상 스크립트가 대신 켜지 않는다. 이 경로는 debug emulator 전용이며 SDK 실패 후 몰래 대체하지 않는다. 콘솔에 제어 경로와 합성 음성 시험을 표시한다. 실제 차량 SDK 제어 완성은 남은 제약으로 기록한다.

변경 후에도 앱 자동 시작 동작, 요청/관측 분리, 중복 요청 방지, 실패 시 다른 지원 유지라는 검수 기준은 동일하다. 에어백 자동 실행·Gleo 선제 호출·실차 제어의 검증은 이번 범위 밖이다.


### 구현 중 신호 의미 검수

에뮬레이터의 HAZARD_LIGHTS_STATE는 스위치 활성 상태가 아니라 500ms 주기의 실제 점멸 위상(0/1)이었다. 1초 단발 조회는 꺼진 위상만 연속 관측할 수 있었다. SWITCH=1을 확인한 뒤 150ms 간격의 제한된 관측 창에서 실제 STATE=1을 함께 확인하도록 수정한다. 스위치만 켜졌다고 체크하지 않으며 실제 점멸을 관측하지 못하면 미확인이다. 원시 로그와 실행 결과를 검수 기록에 보존한다.

## 추가 요청: 전방 충돌 편과 통합 영상

사용자 요청: 전방 충돌에서 트렁크 자동 개방을 보여 주는 영상을 후방 충돌 편에 이어 붙이고, 동작을 설명하는 자막을 추가한다.

### 계획 및 검수

전방 충돌이라는 사실만으로 후방 공간·손상·개방 안전을 추정하지 않는다. 별도 `rearClearConfirmed` 입력을 조건으로 받는다. 재현 콘솔에서 이 조건을 명시하고, 정상 사례는 전방 충돌 + 실제 정차(P·속도 0) + 이동 가능 응답 + 후방 개방 공간 확인 후 앱이 자동으로 트렁크 개방을 1회 요청한다. 현재 공개 센서로 후방 공간을 판별했다는 주장을 하지 않는다. 공간 불명, 이동 중, 도움 요청, 이미 이동 시작, 재생성/중복 이벤트에서는 자동 명령을 내지 않거나 반복하지 않는다.

후방 편은 기존 보류 흐름을 유지한다. 전방 편은 실제 SDK 트렁크 제어와 readback, Pleos 차량 그림의 트렁크 열림, 현황판의 체크를 함께 보여 준다. 다음/개방 확인 버튼은 누르지 않는다. 자동 개방 시도 기록은 사건과 함께 저장한다.

추가 검수: 조건 불충족이면 명령 0회, 정상 전방 사례 명령 1회·실제 열림, 재시작/테마 변경 재실행 없음, 후방 기존 사례 명령 0회 유지. 통과 후 전방 편 촬영. 두 영상을 후방 → 전방 순서로 합치고 실제 단계 시각에 맞춘 설명 자막을 넣는다. 자막은 “후방 충돌: 트렁크 개방 보류”, “정차와 후방 공간 확인 후 자동 개방”처럼 기능과 이유를 설명한다. “시연 영상” 등의 소개 문구를 사용하지 않는다.

완료 산출물: 공유 작업 폴더의 `output/safetystep/automatic/SafetyStep-0.5-automatic.mp4`, 1분 58초. 후방 → 전방, 설명 자막 21개, 실제 화면 유지. 정상 원본의 하차 후 상태 정리 대기 구간만 줄였다. 단계별 결과와 연동 경계는 `safetystep-automatic-validation.md`에 기록한다.
