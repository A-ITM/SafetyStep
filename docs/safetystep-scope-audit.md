# 세이프티스탭 개발 범위·과설계 검토

> 후속 반영: 이 검토의 축소 방향을 [Phase별 실행 계획 1.3](safetystep-execution-plan.md)에 반영했다. 아래 본문은 권고 당시의 판단 기록이며 실제 작업 범위·완료 기준은 1.3을 따른다.

2026-11-17 · 검토 대상: 서비스 설계 1.1과 현재 0.5 구현

## 1. 판단

**첫 제품 기준으로 일부가 과하다. 가장 큰 문제는 기능 하나의 복잡성보다, 효과 검증·다양한 도로 대응·실시간 전파·운영 계측을 같은 출시 묶음으로 잡은 점이다.** 특히 1.1의 Phase 3에는 공공 API, 지도 매칭, 인증, DB, 대상 전파, 종료, 우선도, 재경고, 이용 계측이 한꺼번에 들어 있다.

이번 판단에서 첫 제품은 **지원되는 Pleos 환경과 명시한 도로 범위에서 실제 안내·공공 경고·자체 사건 전달을 검증할 수 있는 소규모 파일럿**이다. 전국·다차종·기관 공동 운영으로 확대할 때는 아래에서 미루는 일부 기능이 필요해진다.

권고는 다음과 같다.

- 첫 행동 안내와 뒤차 경고라는 목적, 실제 관측 원칙, 인증·종료·신선도 구분은 유지한다.
- 구현 수단은 작은 앱 처리부와 서버가 범위를 걸러 주는 HTTP 조회로 시작한다.
- 공유 위험도 차등·감속 기반 재경고는 목적과 연결되는 가설이지만, 첫 경고 품질을 확인한 뒤 실험 기능으로 추가한다.
- MAU·유지율에 필요한 이벤트는 남기되 계정 통합·운영 대시보드를 미리 만들지 않는다.
- 51개 검수 항목은 요구와 예외의 목록으로 보존한다. 모두 별도의 종단 시험 자동화 프로젝트로 구현하지 않는다.

이 문서는 **축소 권고안**이다. 기존 1.1의 합의·약속을 조용히 삭제하지 않았으며, 앱 코드·배포 범위도 변경하지 않았다. 아래 권고를 채택할 때 상세 문서의 우선순위와 완료 기준을 함께 갱신해야 한다.

## 4. 백엔드 단순화의 구체적인 범위

가장 먼저 바꿀 설계는 **‘누가 무엇을 받았는지 계속 저장하는 구독 서버’에서 ‘요청 시 현재 범위만 조회하는 서버’로 좁히는 것**이다. 이는 1.1의 수신 등록 구현 방식을 바꾸는 제안이므로 팀 합의 후 API 계약에 반영한다.

1. 앱은 위치·방향·관측 시각·구간 후보를 요청에 보낸다. 서버는 인증과 입력 품질, 지원 도로·허용 범위를 검증해 관련 사건만 반환한다. 클라이언트가 보낸 임의 범위를 그대로 믿지 않는다. 인증만으로 실제 GPS 위치를 입증할 수 있다는 주장은 하지 않는다.
2. 응답에는 최소한 사건 ID·버전·상태·위치·출처·관측 시각·신선도, 조회 범위·완전성·서버 시각을 둔다. 한 응답에 해당 범위의 전체 결과를 담는 크기부터 시작한다. 한도를 넘으면 불완전 결과로 실패 처리하며 잘린 목록을 완전 목록으로 쓰지 않는다.
3. 조회는 한 번에 하나씩 하고, 구간/방향이 바뀌면 앱의 로컬 contextGeneration을 바꾼다. 이전 구간의 늦은 응답을 버리고 현재 위치로 마지막 경고 조건을 평가한다. 매 위치 tick마다 세대를 바꿔 응답이 영원히 폐기되지 않도록 구간 변경과 위치 갱신을 구분한다.
4. 사건 생성·갱신에는 고유 요청 ID, 소유/권한 검사, 사건별 version을 유지한다. 서버 재시작 후 사건·종료 기록을 보존한다. 이 데이터와 차량별 전달 이력은 서로 다르다.
5. 최초 연결·구간 진입·재연결은 최신 범위 목록을 조회하면 된다. 별도의 서버 구독 가입·해지·lease 갱신은 첫 HTTP 버전에서 생략할 수 있다.
6. 오래된 ACTIVE를 TTL로 삭제하지 않고 해당 범위 목록에서 STALE로 구분한다. 종료는 상태로 처리하고 정해진 보관 기간 동안 기록한다. 실제 게시·보관 정책이 없는 채 무기한 유지하거나 임의 종료하지 않는다.
7. 같은 구간의 완전 목록에서 사라진 항목은 ‘현재 조회 범위의 게시 대상 아님’으로 처리한다. 종료 사실을 알려야 하는 경우 명시적인 종료 레코드가 필요하다. **목록 부재를 RESOLVED로 추론하지 않는다.** 구간 이탈의 로컬 안내 해제, 통신 실패의 미확인, 만료의 STALE 규칙은 유지한다.

이 범위에서는 `membershipGeneration`의 서버 저장, lease, 차량별 전달 이력, `knownIncidentIds` 검증, 제거 사유 응답을 한꺼번에 만들 필요가 줄어든다. 반면 완전성·로컬 세대·사건 버전까지 없애는 것은 권하지 않는다. 범위 밖 전송은 ‘서버가 검증한 요청 위치 기준’으로 시험하고 실제 위치 오차·업데이트 지연은 별도 측정한다.

수신 구간의 지속 추적이나 상세 push가 필요해지면 수신 등록을 다시 도입한다. Supabase Realtime도 채널 권한과 재검증 시점이 있으므로, 연결을 추가하는 것만으로 이 문제들이 해결되지 않는다. [Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization)

## 5. Android는 필요한 부분만 분리한다

현재 코드는 `PrototypeViewModel` 673줄, `Incident` 84줄, `SafetyStepState` 52줄, `HazardClient`/저장 코드 133줄, 응답 해석 26줄, 좌석 정책 39줄 규모다. 줄 수만으로 품질을 판정하지는 않지만, 이미 VehicleGateway·SpeechGateway·정책 함수가 있어 전면 재설계의 근거는 약하다.

권장 구조는 같은 앱 모듈 안에서 다음 정도다.

- 지원 세션 처리부 하나: 안내·도움·좌석 상태를 갱신하고 화면에 현재 상태 제공.
- 기존 VehicleGateway와 SpeechGateway: 실제 SDK·시험 입력 경계 유지.
- 사건 저장/전송 처리부: 로컬 상태·대기열과 서버 조회/쓰기를 담당.
- 부작용 없는 작은 정책 함수: 제어 조건·잔류 판정·경고 여부를 시험.

화면 생명주기와 필요한 지원 작업을 분리하는 것은 정당하다. 다만 상태 축마다 별도 서비스·범용 workflow 엔진·Gradle 모듈을 만드는 것은 필요하지 않다. 1.1도 그런 배포 구조를 요구한 것은 아니며, 구현 시 과하게 해석하지 말아야 한다. Android 공식 가이드도 앱 상황에 맞춰 아키텍처를 적용하도록 하고, domain layer는 재사용·ViewModel 복잡성을 줄일 필요에 따라 권장한다. [Android 아키텍처 권고](https://developer.android.com/topic/architecture/recommendations)

## 6. 큰 설계 전에 고칠 수 있는 실제 문제

코드에서 `setForeground(false)`는 차량 관측·네트워크·음성을 멈춘다. 지원되는 실행 상태에서 사고 지원과 화면 표시를 분리하는 작업은 계속 필요하다. 자동 기동 권한을 확인하지 않고 ‘일단 화면 켜진 경우만’으로 제품의 자동 대응이 완성됐다고 할 수는 없다.

또한 현재 통신 루프는 `syncNetwork()`가 끝난 뒤 `delay(2000)`을 수행한다. `syncNetwork()`는 전송 대기열을 먼저 비운 다음 사건 목록을 조회한다. 따라서 **현재 코드의 2초는 조회 간격 상한이 아니다. 업로드·연결·응답 지연까지 더해진다.**

먼저 업로드 재시도가 수신 조회를 밀지 않도록 작업을 나누고, 실제 조회 시작 간격·서버 접수·음성 완료 시각을 기록하는 것이 유용하다. 느린 요청을 무한 병렬화하지 않고 지연 초과를 드러낸다. 1.1의 단계별 0.5초·1초 예산은 초기 가설로 두고, 핵심 N/Y를 유지하면서 측정으로 조정한다. 각 내부 배분값을 영구적인 별도 출시 조건으로 고정할 필요는 없다.

근거: [현재 통신·실행 코드](https://github.com/A-ITM/SafetyStep/blob/78b0fddac8f41529747825d7c3b7759acbcd1206/android/app/src/main/java/io/github/aitm/pleosapp/prototype/PrototypeViewModel.kt#L474), [HTTP 요청 구현](https://github.com/A-ITM/SafetyStep/blob/78b0fddac8f41529747825d7c3b7759acbcd1206/android/app/src/main/java/io/github/aitm/pleosapp/prototype/HazardClient.kt#L19).

## 7. 첫 제품을 세 작업 묶음으로 줄이는 안

| 묶음 | 구현 | 완료 판단 |
| --- | --- | --- |
| A. 사고 차량의 행동 지원 | 첫 행동 안내, 비상등 읽기·안내, 도움 요청, 잔류 알림, 신고 위치, 지원/도로 상태 분리, 기본 로그 | 실제 마이크와 차량 관측으로 동작. 정상·무응답에서 N 측정, 도움/오류/잔류 분기 통과 |
| B. 실제 기본 경고와 자체 전파 | 공공 1종, 선정 도로 매칭, 인증·사건 DB, 서버 범위 조회, 자체 제보·갱신·종료, 한 가지 경고 정책 | 주행 UX에서 경고 수신·음성 확인, Y 측정, 진입/이탈/재연결/만료/개별 종료 통과 |
| C. 효과 비교와 개선 | 고정 안내 모드, 이벤트 내보내기, 소규모 파일럿 후 약 20명 비교, 활성 주행 이벤트 | 첫 행동·누락·조작·경고 지연 결과 확보. MAU/유지율은 실제 관측 기간만 집계 |

API 이용 조건·자동 기동·음성·차량 권한은 A/B 착수와 함께 조기에 확인한다. 전체 그림의 선행조건이 되는 지원 불가를 늦게 발견하지 않기 위해서다. 공공 연동이 완료되지 않았다면 B는 완료로 표시하지 않는다.

트렁크, 조기 우선도 차등, 감속 기반 재경고, 복잡 도로 지원, Realtime은 A/B의 실제 실패·평가 자료를 보고 별도 추가한다. 기존 제안에서 목적에 중요한 아이디어를 첫 출시 필수와 실험 후보로 구분하는 변경이다.

## 8. 검수도 구현 형태를 줄인다

51개 항목이 있다는 사실 자체는 과설계가 아니다. 값 누락·무응답·오래된 사건 같은 경계조건은 적은 코드로 여러 사례를 검사할 수 있다.

| 검수 방식 | 묶을 내용 |
| --- | --- |
| 작은 정책 단위 시험 | 부정/도움 표현, 좌석 불명·누락, 경고 방향·거리, 제어 금지 조건 |
| 서버 계약 시험 | 범위 밖 제외, 버전·중복, 인증, 진입 목록, 만료와 종료, 여러 사건 중 하나 종료 |
| 소수의 실제 연속 실행 | 첫 안내·실제 마이크·잔류·신고 위치, 주행 경고·종단 지연, 중단·복귀 |
| 시험 기능 도입 때 추가 | 트렁크, Realtime 권한 회수, 우선도 변경·재경고 |
| 간단 집계 fixture | 활성 주행 중복 제거·코호트 날짜 경계·결측 처리 |

새 축소 계약에서는 1.1의 수신 등록·removals 전용 시험을 그대로 구현하지 않고, 같은 요구를 새 HTTP 계약으로 증명하도록 바꾼다. 미구현 기능을 테스트 통과로 처리하지 않는다. 실제 사람의 이해·행동 평가는 자동화 로그가 대신하지 못한다.

## 9. 검토 결과의 적용 범위

줄일 비용의 중심은 **구독 서버의 상태 관리, 범용 지도 처리, 검증 전 차등 경고, 운영 분석 체계**다. 유지할 비용의 중심은 **핵심 자동 흐름, 실제 신호/음성, 권한·신선도·종료, 첫 안내와 뒤차 경고의 효과 검증**이다.

현재 정보만으로 개발 기간이나 절감 비율을 수치로 추정하지 않았다. 팀 가용 시간·API 응답 품질·실제 SDK 지원이 확인되지 않았기 때문이다. 먼저 A/B에 필요한 지원 범위를 검증하고, 실제 작업 단위로 추정하는 것이 적절하다.
